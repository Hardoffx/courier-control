## Цель продукта

Веб-система для ежедневной работы службы курьерской доставки медицинских материалов. Она заменяет пересылку статичной Excel/картинки на живой маршрутный лист, сохраняя привычную для руководства табличную модель работы.

Один backend/database, два интерфейса:
- диспетчер/руководитель;
- курьер с мобильного телефона.

Отдельный старый Telegram-проект `courier-route-bot` не менять без прямого запроса. `courier-control` — самостоятельный продукт.

## Зафиксированные продуктовые решения

- Django 5.2, PostgreSQL production, Django templates, минимальный JS, openpyxl.
- Не вводить React/Vue/DRF до появления реальной необходимости.
- Django Admin — технический fallback, основной интерфейс диспетчера кастомный.
- Интерфейс руководства должен напоминать привычный Excel: № → объект/код → адрес → тип → курьер → временное окно → телефон → статус.
- Цвет строки — только визуальная пометка пользователя. НИКОГДА не использовать цвет для определения лаборатории, статуса, маршрутизации или статистики.
- Тип точки определяется данными/справочником: CMD обычно числовой код; ИНВИТРО — текстовое обозначение точки; сторонние лаборатории имеют собственные названия; склад/офис/возвраты — служебные точки. Текущая эвристика — лишь fallback и позже должна уступить справочнику.
- GPS фиксируется при завершении доставки, если браузер разрешил. Отказ/таймаут GPS не должен блокировать завершение.
- Excel остаётся главным входом для руководства на MVP; OCR/фото — fallback и отдельный Telegram workflow.

## Реализовано

### Основа
- custom `accounts.User` с ролями dispatcher/courier и телефоном;
- первоначальные migrations для accounts и deliveries;
- Delivery, DeliveryPoint, DeliveryEvent;
- SQLite fallback локально, PostgreSQL через env в production;
- Whitenoise, Gunicorn requirements, `.env.example`, `.gitignore`.

### Delivery / справочник
- дата, адрес, организация, получатель, телефон, комментарий;
- courier, route_order;
- new / in_progress / done / problem;
- problem_reason, completed_at, completion latitude/longitude;
- source_label, time_window, row_color;
- DeliveryPoint: CMD / INVITRO / external / service / unknown;
- audit trail DeliveryEvent.

### Диспетчер
- dashboard текущего дня;
- статистика статусов и курьеров;
- создание/редактирование точки;
- Excel import;
- массовое назначение выбранных строк курьеру;
- автоматический new → in_progress при назначении и обратный переход при снятии назначения;
- быстрое редактирование строки: объект/код, адрес, время, телефон, цвет;
- поиск по коду/адресу/телефону/организации/получателю;
- фильтры по типу точки, статусу, курьеру/неназначенным;
- цветные строки как независимое оформление.

### Курьер
- мобильный список на сегодня;
- прогресс;
- ссылка в Яндекс Карты;
- click-to-call;
- завершение с попыткой получить GPS и fallback без GPS;
- проблема;
- добавление телефона;
- изменение порядка оставшихся точек вверх/вниз; порядок после перестановки перенумеровывается.

### Excel
- обязательный Address/Адрес;
- aliases для объекта/кода/точки, времени, телефона, комментария, курьера, порядка, даты и т.д.;
- начальная классификация CMD/INVITRO/external/service;
- создание/использование DeliveryPoint;
- попытка сохранить знакомые Excel fill colors в `row_color`;
- цвет не участвует в классификации.

### Инженерия
- GitHub Actions CI добавлен: install requirements, `manage.py check`, `makemigrations --check`, migrate, tests.

## Важные технические долги / риски

1. `Delivery.infer_point_kind()` пока эвристический. Проверить реальными справочниками; `МО ...` нельзя навсегда считать достаточным признаком INVITRO.
2. `DeliveryPoint` unique `(code,address)` для non-CMD с пустым code может объединять разные именованные точки по одному адресу. Пересмотреть после появления реальных справочников.
3. При quick edit source_label/address связанный `DeliveryPoint` пока не пересинхронизируется автоматически.
4. Excel fill parser ограничен RGB-палитрой и смотрит адресную ячейку; theme/indexed fills и иные варианты пока не покрыты.
5. Нужны полноценные automated tests. CI создан, но тестовое покрытие ещё минимально/отсутствует.
6. Проверить GitHub Actions после первого запуска и исправить любые migration/system-check ошибки.
7. Код `deliveries/views.py` сейчас функциональный, но слишком плотный; перед production разделить import/services/query logic для сопровождаемости.
8. Production deployment, домен, HTTPS, PostgreSQL, static files и bootstrap users ещё не завершены.
